📐 屬性 (Attribute)
= Column / Field 欄位
表中每一直行,例如 Name、Class。每個屬性有自己嘅資料類型。
📄 元組 (Tuple)
= Row / Record 紀錄
表中每一橫行(藍色嗰行)代表一個實體例如一位學生。
🔑 主鍵 (Primary Key, PK)
唯一識別嘅欄位
用嚟唯一識別每一行。值必須唯一且非 NULL。每張表只有一個 PK。
🟣 候選鍵 (Candidate Key, CK)
有資格做主鍵嘅欄位
所有可以做主鍵嘅欄位,值都唯一。最後揀其中一個做 PK,其他叫 Alternate Key。
🟠 外鍵 (Foreign Key, FK)
指向另一張表嘅 PK
用嚟連接兩張表(關係)。例如 STUDENT.ClubID 指向 CLUB 表嘅主鍵 ClubID,代表「學生屬於邊個學會」。

➡️ 功能依賴 (Functional Dependency, FD)

當 A 嘅值能唯一決定 B 嘅值,我哋寫成:

A → B

讀作:「A 決定 B」或「B 功能依賴於 A」

🌰 例子

SID → Name, Class

畀我學生編號 S101,我可以肯定知道佢叫陳大文,讀 5A。

⚠️ 呢張表會引起 4 種問題

統稱「異常 (Anomalies)」
📥
1. 插入異常 (Insertion Anomaly)
想加新資料但加唔到
想新增一個部門 D30 人事部,但暫時冇員工 → 因為冇 EmpID(主鍵)就無法插入新行。
✏️
2. 更新異常 (Update Anomaly)
改一個值要改好多次
市場部換經理:王經理 → 陳經理。表入面市場部出現 3 次,要逐行改。漏改一行會導致資料不一致。
🗑️
3. 刪除異常 (Deletion Anomaly)
刪一個值連帶刪埋第二個
如果張志豪 (E003) 離職,刪除佢嘅紀錄時,連帶 「財務部 / 李經理」 嘅資料一齊消失。
📋
4. 資料重複 (Data Redundancy)
同樣資料儲存好多次
「市場部 / 王經理」喺表入面重複咗 3 次。資料越多,佔用嘅空間就越大。

💡 解決方法:規範化 (Normalization)

用「三道門檻」一步一步將表整齊化

🎯 規範化嘅目標

① 減少資料重複(節省儲存空間,易維護)

② 避免三大異常(插入、更新、刪除唔再出錯)

③ 提高資料完整性(避免矛盾、保持一致)

🚪 三道門檻 (1NF → 2NF → 3NF)

每一道門檻處理一種特定問題,逐步將表拆得越嚟越整齊。大部分商業系統做到 3NF 已經足夠!

解決一格多值 + 重複群組
➡️
🔗 2NF
解決部分相依
➡️

解決遞移相依

⚛️ 第一範式 1NF — 兩大規則

Atomic Values & No Repeating Groups

規則 ①:原子值 (Atomic Value)

每一格 (cell) 只可以儲存 一個不可再分割的數值。

規則 ②:無重複群組 (No Repeating Groups)

同一資料不可以用 多個欄位(例如 Phone1、Phone2、Phone3)重複出現。

💡 簡單記憶法

「一格一值,一欄一概念」 — 每格只放一個值,每欄只代表一種概念。

🔗 第二範式 2NF — 消除部分相依

Eliminate Partial Dependency

條件 ①:已經符合 1NF

每格放一個原子值,無重複群組。

條件 ②:無部分相依 (No Partial Dependency)

所有非主鍵欄位必須完全相依於整個主鍵,不可以只依賴主鍵嘅一部分。

⚠️ 重要前提

2NF 嘅問題只會出現喺 複合主鍵 (Composite Key) 嘅表格。若主鍵只係 單一欄位,根本無「部分」可言,自動符合 2NF!

"要靠就靠晒,唔可以淨係靠半個"
非主鍵屬性必須依賴整個主鍵

🔄 第三範式 3NF — 消除遞移相依

Eliminate Transitive Dependency

條件 ①:已經符合 2NF

已是 1NF + 無部分相依。

條件 ②:無遞移相依 (No Transitive Dependency)

非主鍵欄位之間不能互相決定,所有非主鍵欄位必須直接依賴主鍵。

📌 什麼是「遞移相依」?

當 非主鍵 A → 非主鍵 B,而 B 又依賴主鍵時,就形成「主鍵 → A → B」嘅鏈條。呢種「轉手相依」就叫 遞移相依。

"淨係聽老闆話,唔聽同事話"
非主鍵欄位只可以直接聽主鍵指揮
